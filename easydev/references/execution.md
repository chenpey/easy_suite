# 执行与验证

## 任务基线与写入范围

- 查看项目规则与 Git 状态（含 staged/unstaged/untracked）；第一次采集基线用一条命令合并状态与提交检查（如 `git status --short --untracked-files=all && git rev-parse --verify HEAD 2>/dev/null`）。有 `HEAD` 记录它，但不能代替用户已有修改；无 Git 或无首次提交时用文件内容基线。
- 编辑前记录文件路径与存在状态。干净已跟踪文件可从已记录提交重建，直接复用该 Git 基线，无需另存；已有 staged/unstaged 改动、未跟踪、无 Git/首次提交或不能可靠重建时，在任务目录 `baseline/` 按**仓库相对路径**（如 `baseline/service-a/.env`）保存首次原内容（不能只存哈希；同名文件不覆盖，后续编辑不覆盖首次基线）。扩大写入范围前补记录；新建记“原先不存在”，删除/重命名保留来源基线。
- 仅覆盖本任务基线范围，不复制全仓、无关凭证或大型资源；只读审查不备份代码。保留至本次验收或交接结束，敏感快照不入库或发给无关代理。
- 对比基线与 Git 状态（含增删）识别本次修改；归属不明先核实，不自动回退用户内容；禁止为整理基线自动 `stash`/`reset`/`checkout` 或改索引。快照只用于归因与审查，不授权整体恢复；修正越界只撤销已确认属本任务的部分，遇用户或其他会话并发修改同一位置时保留其工作并协调冲突。

## 任务目录与恢复

非敏感记录优先用宿主任 artifact/scratch 目录；否则用系统临时目录 `easydev/<repo-id>/<task-id>/`（`repo-id` 取项目绝对路径稳定摘要，`task-id` 用宿主任务 ID 或新生成唯一 ID），创建后在交接/会话中记录绝对路径，不猜旧目录。

敏感原内容（如含凭证的 `.env`）严禁写入会展示、上传或同步的 artifact 目录。优先在确认不同步的系统临时位置使用新建且权限受控的私有目录（POSIX 目录 `0700`、文件 `0600`，其他平台用等效 ACL；临时目录名本身不证明私密）。备份与复用须满足前置校验：① 仅接受仓库内规范相对路径（拒绝绝对路径与 `..` 越界）；② 写入或复用前逐级核验任务私有根、`baseline/` 及目标父目录链均为**非符号链接的真实目录**，并将目录权限全部收紧为 `0700`；③ 目标不存在时以 `0600` 创建普通文件写入首次原内容；目标已存在时必须确认为**非符号链接的普通文件**并收紧为 `0600`（保留首次基线不覆盖），若为目录、符号链接或异常类型则立即报错停止。无法确认保护条件时暂停对该文件的写入并说明限制，不复制到未知位置。共享账本仅记路径/存在状态，不记敏感内容；跨会话恢复不授权上传敏感快照。

账本为 `ledger.md`，非敏感原内容放 `baseline/`，探针产物放 `spike/` 并标 `throwaway`。恢复由交接提供账本路径；路径丢失或临时目录已清理时先核实原基线与预算，不默认为新任务或虚称可恢复。需长期保留用宿主持久 artifact（无则说明限制）。未验收或仍有阻塞时不自动清理；确认无需恢复后按宿主权限清理本任务产物，不将快照/探针移入产品仓库。

## 最小充分实现

先找现成模式和全部受影响入口，定位并修复**实际违反契约的位置**（共享解析器、基类、状态机或 helper 失守时修共享源头并核对读/写、序列化/反序列化、同步/异步等对称分支；特定调用方传参或使用违约时修调用方，不在无辜下游打掩盖上游错误的表层补丁）。范围与难度按任务定，不看文件数；不顺带清理历史债。改动前确认可能破坏或暴露的用户数据及会失效的调用方。

按序取第一个能完整解决问题的方案：
1. 需要存在吗？没人要求的功能、选项和灵活性直接跳过并用一行说明（不得跳过用户明确要求的内容；高风险改动仍按规则进入 `full`）；需求含糊时先做完成核心工作的最小版本。
2. 本项目已有实现（helper、组件、服务、既有模式）？按周围用法复用。
3. 标准库或平台能力？优先使用，除非项目已有更合适的自家实现。
4. 已安装依赖？用现成的，不为少写几行引新依赖；新依赖须解决现有能力无法合理覆盖的需求。
5. 选择一眼能懂的直接写法；简单表达式用一行，分支与状态变化展开写清。
6. 补齐需求所需的最小代码，以理解和修改成本衡量简洁。

- 懒在方案、不懒在改动：受影响的调用方、测试、配置、导出一次补齐，不留半成品。
- 复用项目分层、接口与约定，值保持平台原生形式；抽象仅服务复用或降复杂度。命名表达业务含义，职责集中；删除冗余保留必要行为，移动/合并代码保留原错误处理与校验。同规模方案选边界更正确的。
- 注释简要解释代码无法直接表达的原因、单位、约束、边界或取舍，关键算法与安全条件写全；行为变化时同步说明，保留有效解释与无关已有注释。已知取舍就地标 `shortcut: <限制>, <升级条件>`，不用 `TODO` 掩盖验收缺口。
- **不得削减**：信任边界输入校验、防数据丢失的错误处理、安全与隐私、可访问性、真实硬件校准及用户明确要求的内容。

## 文档与人工接手

在项目已有位置维护一份权威说明，用正向陈述讲清当前行为、用法、适用条件与异常处理，保留关键契约、参数与单位、必要步骤、验证方法和已知限制（明确禁止条件仍直说）。实现变化时同步注释、示例和文档；相同规则用链接引用，历史记录保留当时事实。

交付前检查接手者能否找到入口、理解约束并运行验证；优先修正理解障碍、失实说明和重复逻辑，不把代码/注释/文档篇幅当质量目标或触发范围外重写。

## 修复尝试与路径切换

一次尝试从提交候选修复开始，附验证结果（测试、静态契约检查或复审），记录成功、失败、证据不足或环境受阻。纯调查不计次；环境故障不耗修复预算（保留候选，不借机反复重写）。每次失败先回退取证，后续尝试须有新证据。预算耗尽时须说明目标不变量、已暴露耦合位置及最小修复是否成立，不单凭失败次数推断必须重写架构。

- `quick` 及未入 `full` 的 `debug` 修复：同一问题最多三次有新证据尝试，不应用模型配置的 `upgrades`，不因单次失败强制委派；到顶停止自动修复并报告证据、缺口及上述三项诊断。
- 风险或范围实质变化时按入口分流进入 `full`；同一账本分别记 `full` 前尝试数与 `full` 阶段·次数，既有 `quick` 历史不占 `full` 阶段 0 或无 `upgrades` 时的三次预算。此后 `full` 预算不因再切路径、换实例或换问题名重置；不得仅为绕过 `quick` 上限而转 `full`。`full` 的阶段次数、正式审核轮次与停止条件见 [编排规则](orchestration.md#升级与停止)。

## 处理审查反馈

开发者先对照需求、代码与测试核实发现；信息不足由主代理补上下文或最小验证，仅需用户决定的部分按 [人工介入规则](planning.md#澄清与人工介入) 提问，独立已确认修复继续。按“阻断/安全 → 简单 → 复杂”顺序一次改一项并验证。若建议破坏现有行为、超范围、违背 YAGNI 或缺上下文，用代码、契约或测试有据反驳并交主代理核实；主代理兼作者时，排除、降级、转风险或移出仍按 [编排规则](orchestration.md#审查和修复) 交独立确认。用户已有架构决策优先。

## 测试选择

- **新功能与非平凡行为**：先写最小失败测试（红），确认失败原因是“功能缺失”而非语法错误，再写最小实现（绿）并重构；原型、生成代码、纯配置与低影响文字/样式除外（无法构造失败测试时依契约或静态链路分析并记未确认条件）。
- **Bug 修复**：先构造复现原症状的回归检查并确认修复前失败；无法复现时依明确契约或静态链路分析并记未确认条件，不把推测当已证实根因。已有有效红测直接复用，不为补历史 TDD 回滚用户已有工作（需验旧版时在隔离副本运行）。
- **覆盖与高风险**：非平凡逻辑至少保留一项有意义的行为测试或断言自检（覆盖验收、边界、错误处理或业务不变量，不镜像实现，不引入无关测试框架）。触及 [高风险边界](../SKILL.md#入口与任务分流) 时核对失败分支、授权边界、重复执行与版本共存，用隔离数据、禁碰生产数据。
- **重构与性能**：重构验证原契约与关键行为保持；性能优化先取可比基线，注明数据量、环境、负载与测量法，不凭主观宣布加速。优先跑项目既有检查，仅在范围、项目要求、新失败或未解决疑点需要时扩大测试；环境失败与代码失败分开，不盲改代码修工具故障。

## 证据

记录实际命令、工作目录、退出状态、关键输出与对应版本/快照。长输出存可回查位置，上下文读摘要、片段与路径；错误堆栈、精确参数和契约保留原文，摘要不足回查全文。凭证脱敏并受权限保护，敏感原内容不入共享交接。子代理报通过时主代理核对可查输出与当前 diff，证据不足才补跑。

回归测试须记修复前失败、修复后通过两次输出（仅跑过一次不证能拦回归）。同版本、同环境的有效检查可复用，不按消息或审查轮次重复全量；受后续改动影响的检查必须重跑，未受影响结果不称覆盖新行为。构建通过、lint 通过、测试通过、验收满足分别判定。

## 完成边界

- **quick 已完成**：目标行为满足，按任务类型完成验证（新增/可复现缺陷具红绿记录，重构具行为保持记录，配置与无法动态复现场景具对应检查及限制说明），通过 [交付前三项微自检](../SKILL.md#开始工作)，明确只做自查。
- **full 闭环完成**：目标行为满足、验证通过且范围无遗漏；最终独立审查覆盖完整任务变更，范围内确认缺陷均关闭，关键风险和验收均有证据。不影响验收的 P3 可列为未实施建议（不称“所有发现已处理”）；影响验收项不得按建议跳过。
- **实现已完成、验证受阻**：代码已写但必要检查无法运行或独立审查未完成，说明具体缺口，不称闭环完成。
- **部分完成/待确认**：存在未决缺陷、验收缺口、潜在 P0/P1 待验证风险，或预算耗尽仍有待处理项；用户接受已知风险时保留记录，不改写为无缺陷。

收尾说明结果、必要验证与实质限制；不凭测试数、模型名或无发现推导“保证可发布”。
