# 执行与验证

## 任务基线与写入范围

- 查看项目规则、Git 状态与已存在的 staged/unstaged/untracked 内容；首次采集基线优先用单条命令合并状态与提交检查（如 `git status --short --untracked-files=all && git rev-parse --verify HEAD 2>/dev/null`），避免拆成多次工具调用。有 HEAD 时记录它，无 Git 或无首次提交时用文件内容基线。HEAD 不能代替用户已有修改。
- 编辑前记录将修改文件的路径与存在状态。可从已记录提交可靠重建原内容的干净已跟踪文件，复用该 Git 基线，无需另存副本；已有 staged/unstaged 改动、未跟踪文件、无 Git/无首次提交或不能可靠重建原内容时，在下述任务目录的 `baseline/` 按**仓库相对路径**（如 `baseline/service-a/.env`）保存首次修改前的原内容，不能只存哈希，避免不同目录同名文件互相覆盖，且同一文件后续编辑不得覆盖首次基线。扩大写入范围前补记录；新建文件记录“原先不存在”，删除/重命名保留来源基线。
- 跟踪基线覆盖范围即可，不复制全仓、无关凭证或大型资源。只读审查不必备份代码。保留至本次结果验收或交接结束，敏感快照不放进仓库或发送给不需要它的代理。
- 对比任务基线识别本次修改，并核对 Git 状态及新增/删除清单。无法确定归属时先核实，不自动回退用户内容。禁止为整理基线自动 stash、reset、checkout 或改索引。
- 快照用于归因与审查，不授权整体恢复；修正代理越界改动时只撤销已确认属于本任务的部分。发现用户或其他会话同时修改同一位置时，保留其工作并协调冲突。

## 任务目录与恢复

非敏感记录需要落盘时优先用宿主提供的任务 artifact/scratch 目录；否则使用系统临时目录下 `easydev/<repo-id>/<task-id>/`，repo-id 取项目绝对路径的稳定摘要，task-id 使用宿主任务 ID 或新生成的唯一 ID。创建后在交接/会话中记录实际绝对路径，不猜测旧任务目录。

敏感原内容（如含凭证的 .env）不得写入会展示、上传或同步的 artifact 目录。优先在确认不被同步的系统临时位置使用新建且权限受控的私有目录（POSIX 目录 0700、文件 0600，其他平台使用等效 ACL）；临时目录名称本身不证明私密。备份与复用须满足前置校验：① 仅接受仓库内规范相对路径（拒绝绝对路径与 `..` 越界）；② 写入或复用前逐级核验任务私有根、`baseline/` 及目标父目录链均为**非符号链接的真实目录**，并将目录权限全部收紧为 `0700`；③ 目标尚不存在时以 `0600` 创建普通文件写入首次原内容；目标已存在时必须确认为**非符号链接的普通文件**并收紧为 `0600`（保留首次基线不覆盖），若为目录、符号链接或异常类型则立即报错停止。无法确认保护条件时暂停对该文件的写入并说明限制，不复制到未知位置。共享账本仅记录路径/存在状态，不记录敏感内容；跨会话恢复不因此授权上传敏感快照。

账本保存为 `ledger.md`，非敏感原内容放 `baseline/`，探针产物放 `spike/` 并标注 throwaway。恢复时由交接提供账本路径；若路径丢失或临时目录已被清理，先核实原基线和预算，不能默认为新任务或虚称可恢复。需跨会话长期保留时选用宿主持久 artifact 位置；无此能力则明确临时存储限制。

保留到验收或交接结束；清理仅限本任务产物、确认无需恢复后按宿主权限处理。未验收或仍有阻塞时不自动清理，也不把快照和探针产物移入产品仓库。

## 最小充分实现

先找现成模式和所有受影响入口，定位并修复**实际违反契约的位置**（共享解析器、基类、状态机或 helper 失守时修共享源头，并核对读/写、序列化/反序列化、同步/异步等对称分支；特定调用方传参或使用违约时修调用方，不在无辜下游打掩盖上游错误的表层补丁）。范围与难度由任务决定，不由文件数决定；不搭顺风车清理历史债。改动前确认它可能破坏或暴露的用户数据，以及会失效的调用方。

按顺序取第一个能完整解决问题的方案：

1. 这件事需要存在吗？没人要求的功能、选项和灵活性直接跳过，并用一行说明跳过了什么；需求含糊时先做能完成核心工作的最小版本。
2. 本项目已有实现（helper、组件、服务、既有模式）？按周围代码的用法复用。
3. 标准库或平台能力？用它们，除非项目已有更合适的自家实现。
4. 已安装依赖？用现成的，不为少写几行新增依赖；新依赖必须覆盖现有能力无法合理解决的需求。
5. 选择读者一眼能理解的直接写法；简单表达式用一行，分支与状态变化展开说明。
6. 补齐需求所需的最小代码，以理解和修改成本衡量简洁。

- 懒在方案上，不懒在改动上：调用方、测试、配置、导出等受影响部分一次补齐，不遗留半成品。
- 复用项目分层、接口与约定，值保持平台原生形式；抽象服务于实际复用或复杂度降低。命名表达业务含义，职责集中，相关逻辑便于一起定位。删除冗余时保留必要行为；移动或合并代码时保留原有错误处理与校验。
- 同样大小的方案，选边界情况更正确的那个。
- 注释简要解释代码无法直接表达的原因、单位、约束、边界或取舍；关键算法与安全条件按需写全。行为变化时同步相关说明，保留有效解释与无关的已有注释。
- 已知取舍就地标注 `shortcut: <限制>, <升级条件>`，不用 TODO 掩盖当前验收缺口。

不得削减：信任边界的输入校验、防止数据丢失的错误处理、安全与隐私、可访问性、真实硬件所需的校准，以及用户明确要求的内容。

- 取用顺序第 1 级不得用于跳过用户明确要求的内容；高风险改动仍按路径规则进入 full。

## 文档与人工接手

在项目已有位置维护一份权威说明，用正向陈述讲清当前行为、用法、适用条件与异常处理；保留关键契约、参数与单位、必要步骤、验证方法和已知限制。明确的禁止条件仍直说。实现变化时同步相关注释、示例和文档；相同规则通过链接引用，历史记录保留当时事实。

交付前检查接手者能否找到修改入口、理解关键约束并运行对应验证。优先修正具体理解障碍、失实说明和重复逻辑；代码行数、注释长度或文档篇幅本身不作为质量目标，也不触发范围外重写。

## 修复尝试与路径切换

一次尝试从提交候选修复开始，附验证结果（测试、静态契约检查或复审）；记录成功、失败、证据不足或环境受阻。纯调查不计次；环境故障不消耗修复预算，先保留待验证候选，不借机不断重写补丁。每次失败先回到取证，后续尝试必须有新证据。任何路径的修复预算耗尽时，都须说明目标不变量、已暴露的耦合位置及最小修复是否仍成立；不能仅凭失败次数推断必须重写架构。

- quick 及尚未进入 full 的 debug 修复：同一问题最多三次有新证据的尝试，不应用模型配置中的 upgrades，不因一次失败强制委派。到顶停止自动修复，报告证据、缺口及上述不变量、耦合位置与最小修复是否仍成立。
- 风险或范围实质变化时按入口分流进入 full；同一账本分别记录 full 前尝试数与 full 阶段·次数，已有 quick 历史不占 full 阶段 0 或无 upgrades 时的三次预算，避免误作升级依据。此后 full 的预算不因再切路径、换实例或换问题名称重置；不得仅为了绕过 quick 上限而转 full。
- full 的阶段次数、正式审核轮次及停止条件只见 [编排规则](orchestration.md#升级与停止)。

## 处理审查反馈

开发者先对照需求、代码与测试核实发现，信息不足时由主代理补上下文或最小验证；仅需要用户决定的部分按 [人工介入规则](planning.md#澄清与人工介入) 提问，独立的已确认修复继续。实施顺序为阻断/安全问题、简单修复、复杂修复，一次改一项并验证。建议会破坏现有行为、超出范围、违反 YAGNI 或审查者缺少上下文时，用代码、契约或测试有依据地反驳并交主代理核实；主代理兼任作者时，排除、降级、转风险或移出发现仍按 [编排规则](orchestration.md#审查和修复) 交独立确认。用户已有架构决策优先。

## 测试选择

- 新功能与非平凡行为：先写一个最小失败测试（红），运行并确认它因“功能缺失”失败而不是语法错误，再写最小实现（绿），通过后清理重复（重构）。原型、生成代码、纯配置与低影响文字/样式修改除外；不能构造失败用例时依据契约或静态链路分析并记录未确认条件。
- Bug 修复：先构造能复现原症状的回归检查，并确认它在修复前失败；不能复现时依据明确契约或静态链路分析，记录未确认条件，不能把推测当作已证实根因。
- 已有红测有效时复用，不重写；不为补做历史 TDD 去回滚用户已有工作，需要验证旧版本时在隔离副本运行。
- 非平凡逻辑：至少保留一项有意义的行为测试或断言自检。测试验收、边界、错误处理或业务不变量，不镜像实现，不为低影响文字/样式修改引入测试框架。
- 涉及 [高风险边界](../SKILL.md#入口与任务分流)：核对相应失败分支、授权边界、重复执行与版本共存；使用隔离数据，不对生产数据复现。
- 重构：验证原契约和关键行为保持；性能优化先获取可比较的基线，注明数据量、环境、负载与测量方法，不以主观判断宣布加速。
- 优先执行项目现有的相关检查。只有改动范围、项目要求、新失败或未解决疑点需要时才扩大测试。环境失败与代码失败分开，不盲目改代码解决工具故障。

## 证据

记录实际命令、工作目录、退出状态、关键输出与所对应的代码版本/任务快照。长输出保存到可回查位置，上下文读取结果摘要、相关片段与路径；错误堆栈、精确参数和契约保留原文，摘要不足时回查完整记录。凭证按权限保护与脱敏，敏感原内容不进入共享交接。子代理报告通过时，主代理核对可查验输出及当前 diff；证据不足才补跑。

回归测试须记录修复前失败、修复后通过两次输出；只跑通过一次不能证明该检查能拦截回归。同一版本、同一环境的有效检查可复用，不按每个消息或审查轮次重复全部测试。被后续改动影响的检查必须重跑；未受影响的结果不能被表述为覆盖新行为。构建通过、lint 通过、测试通过、验收满足是不同结论。

## 完成边界

- **quick 已完成**：目标行为满足，按任务类型完成相关验证（新增/可复现缺陷具红绿记录，重构具行为保持记录，配置与无法动态复现的场景具对应检查及限制说明），且通过 [SKILL.md 交付前三项微自检](../SKILL.md#开始工作)（受影响调用方与契约已同步、验证证据匹配当前代码、复核未触及高风险边界或隐含跨模块耦合）；明确只做自查。
- **full 闭环完成**：目标行为满足、相关验证通过且范围无遗漏；最终独立审查覆盖当前完整任务变更，范围内确认缺陷均关闭，关键风险和验收均有证据。不影响验收的 P3 建议可留在建议清单，但须说明未实施，不能称“所有发现已处理”；影响验收的问题不能按建议跳过。
- **实现已完成、验证受阻**：代码已写但必要检查无法运行或独立审查未完成，说明具体缺口，不称闭环完成。
- **部分完成/待确认**：有未解决缺陷、验收缺口、潜在 P0/P1 的待验证风险，或循环预算耗尽且仍有待处理项。用户接受某项已知风险时保留记录，不把接受风险改写为缺陷不存在。

收尾说明结果、必要验证与实质限制；不以测试数量、模型名或无发现推导“保证可发布”。
