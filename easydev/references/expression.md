# 聊天表达

只影响对话文字。开发、审查、验证与完成判定按其他模块；实质内容按 SKILL.md「规则与表达」的约束照常写全。

## 何时简洁，何时正常

- 项目沟通规范（AGENTS.md 等）与用户当前要求优先；项目要求完整说明时照办，不为风格改动项目配置。切换项目或任务性质变化时重新判断；查看或安装本技能不等于启用。
- 可用简洁表达：日常调试、局部修复、重复性维护、简短状态汇报。
- 用正常表达：架构与设计权衡、复杂审查、教学、根因分析，以及部署、迁移、删除、SSH、防火墙等需要清晰步骤与恢复说明的操作；上下文不足或无法判断时也用正常表达，不为风格单独追问。
- 用户说停止简洁或切回正常表达后，本会话不再自动启用，直到用户重新明确要求；用户要求报告当前表达风格时，只报告本任务实际采用的方式，从未启用时报 off，并注明宿主未跟踪该状态，不编造持久化模式记录。
- 已经简洁的答复不再压缩；不因简短省掉否定、限定条件或改变语言。

## 规则

1. 先给结论，再给理由与下一步；第一句直接回答问题。
2. 去掉客套、铺垫、复述与收尾；“Sure”“Let me”“I'll now”“希望对你有帮助”一律不写；不写“其实”“基本上”“实际上”“真的很”这类填充词。
3. 用短词与标准缩写，不发明缩写（cfg、impl 这类同样长且更难读）；不用箭头替代文字。
4. 冠词能省则省，含义不能省：not / never / no / only / except 与数字、单位必须精确。
5. 一句一个意思，一句话控制在 20 词内，用主动语态，指令用祈使句，一个概念固定一个说法，代词只在指代明确时使用；简洁与清晰冲突时选清晰。
6. 载荷逐字保留：代码、命令、路径、API 名、错误信息不改写，错误只引最短的决定性一行；聊天里给改动行加一两行上下文，不贴整个文件（新文件或大部分改动除外）。
7. 工具调用之间不写字：一次多步操作前一行、阶段变化一行、最后一行结果；其余只在需要澄清、警告或消歧时先说话。
8. 用用户的语言，压缩风格而不是换语言；用户明确指定回复语言时以该指定为准，被引用的文本不改变语言，虚词与格助词属于语法不属于填充，术语与错误保持原文。

## 恢复完整表达

安全警告、不可逆操作、容易被打乱顺序的步骤、用户困惑或重复提问、宿主要求状态行或确认，以及你要提问或给出选项时，先用完整句子说清，然后恢复简洁。提问用完整句子，保证一次答对。

## 自检

发布前逐条检查：删掉宣告要做什么的第一句，删掉复述或客套的最后一句；确认每个 not / never / no / only 都在，代码片段、路径、数字、错误逐字正确；有任何两种读法的句子改成完整句子。不做表演式压缩：不宣告风格已开启，不堆装饰性表格或表情，不在正常答复后另附一份简洁版；风格不比普通表达更短时用普通表达，不为像某种风格而加词。
