# 模型配置

按以下顺序选择**第一个存在的完整配置**，不合并多个配置：

1. **用户外部配置（权威来源）**：保存在 Skill 安装目录外，多 harness 共用且更新 Skill 不覆盖。macOS/Linux 为 `$XDG_CONFIG_HOME/easydev/models.json`（`XDG_CONFIG_HOME` 非空时）或 `~/.config/easydev/models.json`；Windows 为 `%APPDATA%/easydev/models.json`（未设置时用主目录下 `.config/easydev/models.json`）。主目录与环境变量以宿主实际提供值为准，不猜其他用户路径。该文件存在时即为强约束：不再改用对话指定的其他文件，也不得按 `inherit` 默认值跳过。
2. 用户在当前对话中明确指定的配置文件路径：仅在外部配置不存在时使用，并在报告中说明；该文件不存在或不可读时报错暂停，不静默回退。
3. 两者都不存在时使用内置默认值：`developer` 与 `reviewer` 均为 `inherit`，`upgrades` 为空。该默认值不依赖任何文件，`inherit` 表示沿用宿主模型与推理深度；此时报告实际来源为“内置 `inherit` 默认值”。

## 强制读取与核对

外部配置存在时必须实际读取并应用，任何角色和路径都不允许跳过：

- 进入 `full`、发起 `review`/`audit` 或任何分派前，先读取并记录实际路径；报告中的来源必须是本次实际读取结果，不能凭“大概没有配置”推断为内置默认值。
- 分派后按工具记录核对实际模型与推理深度（子代理运行记录、事件流等）；与请求值不一致时报告差异、修正后重新分派，不把请求值当作实际值，也不把可查到的信息写成未知。
- 外部配置不存在时才使用内置默认值，并明确写出“外部配置不存在”；无法确认该检查是否执行时不得宣称使用了默认值。
- 用户在当前对话中直接指定某角色的模型或深度（不是指定配置文件路径）属于运行期覆盖，按下方生效范围处理；它不能把“完全不读外部配置”变成合法做法。

分派前报告并读取实际配置路径；外部配置无效、不可读，或对话指定路径不存在时说明报错，不静默回退默认配置（外部配置不存在且用户未指定对话配置文件时才用内置默认值并说明；无法读取用户目录时说明限制，请用户提供可访问配置或确认默认值）。配置是由代理解释的路由偏好，非宿主设置或运行时插件；不自动创建配置文件或修改宿主设置。

`examples/models.*.json` 只是供用户手动复制或参考的示例，永不参与上述优先级；其中 `examples/models.default.json` 是内置默认值的等价模板，仅在需要一个可复制的起始文件时使用。内置默认值已足以让不同 harness 继承宿主模型；只有用户主动修改外部配置时才启用角色分流。

## 字段

- `developer` / `reviewer`：开发修复角色与独立审查/复审角色，均含 `model`、`reasoning_effort`。
- `upgrades`：按序启用的升级阶段，默认空数组，最多两项；每项均含完整的 `developer` 和 `reviewer`，避免角色互换时猜测审核者。
- `model`：`"inherit"` 表示遵循宿主继承规则；接口将 `"inherit"` 作为合法枚举值时原样传入（如 Antigravity `invoke_subagent`），否则省略模型参数，不把字符串 `inherit` 当模型 ID。其他值须为宿主支持的完整模型 ID 或工具暴露的模型层级（如 AGY 的 `flash`/`pro`），实际可用值以 [setup.md](setup.md) 核对的工具接口为准。完整模型 ID 须与宿主模型表逐字一致，并保留 ID 内已有的命名空间前缀（如 `codex/gpt-6.1-sol`）；该前缀不一定是宿主 provider 键名，不按语义拆改。省略前缀的裸写可能无法解析，导致该角色读取失败或退回默认值；宿主要求 `provider/modelId` 组合时按工具接口传入，不改写配置。模型层级（如 AGY 的 `flash`/`pro`）按工具接口原样传入。推理深度写在 `reasoning_effort`，不把 `:high` 之类后缀拼进 `model`。
- `reasoning_effort`：`"inherit"` 表示不覆盖推理深度；其他可填 `none / minimal / low / medium / high / xhigh / max / ultra`（`ultra` 是推理深度，与聊天档位无关），实际有效值以所选模型与工具接口为准，解析通过不代表模型支持。

只接受以上键及类型。选中的配置文件缺失、无效 JSON、空模型名、缺字段、未知键或超过两个升级阶段时，指出错误并暂停依赖配置的分派，其余继续；不静默用旧硬编码路由，不擅改用户文件。

## 生效范围与优先级

1. 宿主工具能力、权限和高优先级指令始终约束调用。
2. 用户当前直接指定某角色的模型/深度（不是指定配置文件路径），按指定范围局部覆盖配置；用户锁定某角色时不得用升级规则绕过，配置不得推翻当前用户指令。指定配置文件路径属于来源选择，按上方顺序：外部配置存在时不改用对话指定文件。
3. 未被用户覆盖的部分取自上述选中的配置文件（缺省继承宿主，不要求特定供应商）。

主代理模型由用户在宿主中选择，本文件只配置被委派的开发与审核角色。`quick`、仅设计/计划与只定位通常由当前代理执行，不强制创建子代理；单次 `review`/`audit` 按 [review.md](review.md) 作者隔离规则执行；`full` 按分工调度（独立性来自不同实例与上下文边界，同模型也不可同实例自审）。默认保留已验证配置，新增调用用于有明确价值的风险检查、独立审查或诊断，先减少重复调用与无关上下文；模型降级、自动路由与输入压缩须经分别评测，不以单次低价或强模型名充当整体收益证据。

开始 `full` 时记录实际配置与宿主限制。任务中改配置后，下次分派前重读，仅影响后续角色，不替换运行中代理、不重置轮次/修复预算（阶段与旧账本不对应时，主代理明确剩余预算）。委派能力、模型/深度可用性、授权与调用故障统一按 [setup.md](setup.md) 处理；本文件只决定请求配置，不证明已生效。

## 升级

初始 `developer`/`reviewer` 为阶段 0，`upgrades[0]` 为阶段 1，`upgrades[1]` 为阶段 2；触发条件、预算与停止规则见 [orchestration.md](orchestration.md)。
