# 编排、独立审查与收敛

仅 full 或明确需要委派时加载。主代理拥有唯一任务状态；流程为：明确验收与基线、开发与验证、冻结修改、独立审查、核实发现、有限修复与复审、交付。

## 角色与模型配置

准备分派前按 [模型配置规则](models.md) 选择并读取用户配置或包内默认值，再按 [setup.md](setup.md) 核对宿主能力与授权。角色和升级顺序只从该配置及用户当前覆盖中获取，不在本规程硬编码供应商或模型。

默认 developer/reviewer 都继承宿主模型。阶段 0 且 developer 的模型与深度均为 inherit 时，主代理可作为唯一开发写入者，仅委派独立 reviewer；配置要求不同开发模型/深度或进入升级阶段时再委派开发者。实现者与审查者必须为不同实例。用户可分别指定模型、推理深度和最多两个升级阶段；每个阶段同时指定开发与审查角色。不同模型家族不是质量保证。

主代理协调目标、基线、交接与发现核实，不与开发代理同时编辑任务代码。默认只有一个写入者。独立只读调查可并行，需有互不重复的目标；不因“复杂”自动启动多位开发者。

## 唯一账本

小任务记在当前上下文；长任务或需要恢复时按 [任务目录与恢复](execution.md#任务目录与恢复) 保存 ledger.md，并在交接中给出绝对路径。至少保留：

- 原始目标、验收、范围、任务基线、用户已有改动与授权。
- 当前阶段、唯一写入者、实际模型/深度、独立审查是否具备条件。
- 审核轮次 `r/4`、每个问题的稳定编号、证据状态、尝试过的修复层级与关闭依据。
- 验证命令、实际结果及对应版本，未覆盖路径与阻塞。

落盘模板（按实际填写，未知项明确写未知）：

```text
目标/验收/范围：
项目路径/任务目录/授权：
基线提交/文件清单/原内容位置/用户已有改动：
阶段/唯一写入者/配置路径/实际模型与深度：
独立审查条件/审核 r/4（占用、受阻或完成）：
问题 ID/证据/full 前尝试数/full 阶段·次数/验证结果/关闭依据：
验证命令/退出状态/输出路径/对应快照：
未覆盖项/阻塞/下一步：
保留与清理状态：
```

父任务、子任务、换代理、换模型、上下文恢复共用账本，不重置计数。大任务可分步实现和验证，在稳定的集成结果上正式送审；不把每个微小任务单独开四轮。多个审核者检查同一冻结版本时合并为一轮，所有结果到齐后再进入修复。

## 交接

只交必要材料：角色与读写边界、项目绝对路径、原始需求与验收、任务基线/本次完整 diff、用户已有内容、适用规则及需读取的模块绝对路径、验证输出、剩余轮数。修复追加问题编号和已核实证据；升级追加失败方案与原因。

明确告知每个子代理：“你是执行角色，不拥有调度权；不要创建子代理、调用完整 easydev、另起审核闭环或重置预算。需要额外帮助时向主代理返回具体子任务。”宿主自动加载入口也不改变角色。

开发者读取 execution，遇到排障读取 debugging；审查者读取 review。不要把所有参考文件和整段会话塞进每个代理。已有的相关技能规则无需重读；不能假设新实例知道上轮结论。

## 审查和修复

1. **准备送审**：开发者停止写入后，主代理对任务基线核对完整变更，包含新增、删除、重命名和未跟踪内容；检查证据对应当前版本。归属不明的改动先调查，不自动撤销。
2. **独立审查**：新审查实例先核对需求与验收，再检查实现质量和相关调用链；合并为同一轮，不为“规范”和“质量”机械增加两次委派。用 [review.md](review.md) 给出有证据的发现及未覆盖部分。
3. **只读隔离**：审查者不修改代码、快照、索引、数据库或外部系统。需要写缓存、生成产物或启动服务的验证，由开发者在隔离位置执行并提供结果；陌生脚本先检查安全性。
4. **核实发现**：主代理追踪证据，确认、排除或转成待验证风险，并记原因。不实施不影响验收的低影响 P3 属延期建议，不构成排除发现，不单独触发确认轮。主代理兼任开发者时，排除、降级、转为待验证风险或以越界为由移出任何发现，必须附代码、契约或测试证据，并交下一轮独立审查者确认；确认前标为“作者有争议、未关闭”。无剩余审核轮次时将争议及证据交用户，不得自行关闭或宣称闭环完成。严重程度与确定性分离；有争议时用最小验证解决，不能为了过审自动接受建议或静默忽略 P2/P3。
5. **修复与复审**：把确认且属于范围内的问题交开发者修复，补足回归证据；复审既核对问题关闭，也查受影响路径。拟通过时在同一轮中通览完整任务 diff，避免局部修复掩盖集成遗漏。

**处理审查反馈**：开发者实施前先对照需求、代码与测试核实发现，不表演式同意；任一建议不清楚时先全部澄清再动手。实施顺序为阻断/安全问题、简单修复、复杂修复，一次改一项并验证。建议会破坏现有行为、超出范围、违反 YAGNI 或审查者缺少上下文时，用代码、契约或测试有依据地反驳并交主代理核实（主代理兼任作者时遵循上述独立确认规则），用户已有架构决策优先。已确认的建议修复后立即补齐验证，不批量无验证修改。

P0/P1 立即优先处理，范围内确认的 P2 同样进入修复。P3 记录具体代价；不影响验收的 P3 作为未实施建议交付，不单独触发修复或复审，用户要求实施时再纳入。区分实质缺陷争议与低影响建议延期：把确定缺陷降级为待验证风险、以越界为由移出发现，或不认领影响验收的问题，仍须按上条附证据并交下一轮独立确认。任何级别的问题只要造成验收缺口，就必须修复或标为未完成，不得靠降级绕过。历史债和越界建议不扩大任务；用户明确接受或延期的缺陷保留为剩余项。

同一审查者可复审以保留问题上下文；上下文丢失、反复漏检或发生实施角色互换时换新实例。审核者不得修复自己要审的版本。

## 升级与停止

尝试定义、路径切换计数和耗尽后的诊断要求统一见 [修复尝试与路径切换](execution.md#修复尝试与路径切换)。本节只定义 full 的升级与审核预算；发现关闭遵循上文独立确认规则。

开发者自测已证明失败或主代理确认关闭证据不足时，可以在两轮审核之间升级，不必先消耗一轮复审；正式复审才消耗审核轮次。扩大范围仍需用户授权。

- 新任务从单次 review/audit 转为授权修复时，先前只读审查仅作为修复前证据，不占 full 正式轮次；修复后首次正式独立审查为 r=1。若该审查原本就是当前 full 的一轮，仍保留已用轮次，不能通过改称 review 重置。
- 默认至多 **4 轮正式审核**：初审一次，复审最多三次。送审前占用一轮并记录受阻/完成状态，工具重连同一次未完成审查不另起新轮。全部并行审查合并计数。
- 配置了 upgrades 时，每个确认问题在当前阶段至多尝试一次修复；原缺陷或症状仍在、或缺少关闭证据时，按数组顺序进入下一阶段，不回退、不重复相同方案。末级修复仍失败即停止，不自动补充模型或重置尝试。用户明确从较高阶段开始时跳过前面的阶段。
- 升级前先确认前任停止写入，并应用该阶段的 developer/reviewer 配对。若新开发模型原先用于审核，重新建立独立审查实例；任何参与实现的实例不得审核该实现。升级阶段在当前任务中保持，不因换问题编号恢复低级配置。
- upgrades 为空时保持当前配置，同一问题最多三次有新证据的修复尝试；换实例不叫能力升级。宿主适配使多个阶段实际上采用相同模型时，仍消耗原阶段预算，不能再获得额外三次机会。独立审核上限始终为四轮。
- 按问题关闭依据、验收缺口和失败症状判断进展；修复旧问题后发现新问题不等于零进展。新问题获得新编号，但不能重置全局审核预算。
- 升级不增加轮数；最后一轮仍有待修缺陷时，报告未完成，不再做没有剩余复审机会的自动修复。必须扩展范围、缺少关键外部信息、终级修复仍无进展或预算到顶时停止自动循环。用户可明确扩大预算或范围，仍沿用原账本。
- 无待修缺陷时按 [execution.md 的完成边界](execution.md#完成边界) 核对状态并立即交付，不凑轮数；P3 建议的处理按上述规则记录。

模型不可用、权限或网络失败不是代码修复失败，不因此消耗修复层级或虚构升级理由；报告实际受阻阶段。剩余授权内且不依赖阻塞的工作继续完成。

## 报告

说明实际完成状态、改动与验证、审核轮数、确认问题及关闭/剩余状态、实质限制。仅当发生升级、角色互换或模型适配时解释原因；模型与深度以工具实际信息为准，未知就标未提供。详细账本用于恢复与追溯，不把整个过程日志堆给用户。
