# 设计与计划

只补足会改变实现的决策。先利用代码、调用方、现有约定和用户已给的条件；设计已确定时在用户请求的交付范围内继续，不重新要求确认。

## 深度选择

| 情况 | 足够的产物 |
| --- | --- |
| 清楚的局部改动 | 一句目标与验证方式，无独立设计文档 |
| 目标清楚、涉及多个步骤 | 简短计划：行为、修改边界、依赖、验证 |
| 新产品行为或多种实质不同方案 | 先列目标/非目标，比较真正有差别的方案并给出推荐与代价 |
| 跨模块重构、协议变更、迁移或长任务 | 可交接设计和计划：契约、数据/状态归属、兼容策略、失败恢复、阶段验收 |
| 只问可行性或快速结论（spike） | 一句待验证问题、最小实验方案、结论或建议；产物按 [任务目录规则](baseline-safety.md#任务目录与恢复) 放入 spike/ 并标注 throwaway，不并入实现 |

脑暴不是固定的开工关卡。只有当问题尚未明确或方案会改变用户体验、兼容、成本及范围时才展开；不为凑选项提出明显较差方案。常规技术选择由代理在已有授权内完成，标明关键假设。

## 澄清与人工介入

把用户意图转换为可观察的结果。先从已有上下文、代码和项目约定消除歧义；需要授权时先查开工记录的授权基线（见 [范围与授权](../SKILL.md#全程约束)），只对未覆盖项请求决定；常规技术选择、需求内修复、审查安排与阶段推进由代理负责，记录会影响结果的假设。只要求设计或计划时交付相应产物，已有实施授权时连续推进。

在以下情况请求用户决定：缺失的产品选择会显著改变结果且无法从上下文确定；操作需要尚未取得的授权；关键验收依赖用户才能提供的信息；或合理修复预算耗尽仍无法可靠完成。宿主明确要求的确认同样适用。问题尽量合并，附已调查事实、推荐与影响；依赖答案的部分暂停，其余工作继续。已有授权持续有效。

## 选项式澄清

意图不清时把可能的解读收敛成有限选项交给用户，不自行选定一种解读继续实现；让用户用序号答复，不用开放式问题换一段需要重新解释的话。

**必须提问**：同一请求存在两种以上互斥解读，且选择改变用户可见行为、公共契约、数据或兼容承诺、成本量级；或该选择落在高风险边界上且没有安全默认值。此时不得“按我的理解先做”，也不得把猜测写进交付当成已确认需求。

**继续实施**：上下文、代码或项目惯例能确定唯一种解读；常规技术选择（命名、内部结构、参数顺序等不影响验收的细节）；可逆且代价低的默认，先按默认实施并在报告标为假设；需求内修复、审查安排与阶段推进。只有不提问会明显增加返工或错误交付时才提问，不为流程完整凑问题。

**格式**：合并成一次提问，最多 3 题；每题 2–4 个互斥选项加「其他（说明）」，首选项由代理给出并标 `[推荐]`、附一行依据；选项描述写可观察结果而非实现术语；每题末尾给一行「未答默认」，默认项必须安全（不产生不可逆、高风险或对外动作），没有安全默认时写「需答复后继续」并列出因此暂停的部分。提问前给出已调查事实（文件与行、既有契约、当前行为），不复述用户已给的信息。

```text
1. 批量导入遇到已存在的记录？
   A [推荐] 跳过重复项并返回跳过数量（现有批量接口同样返回统计，见 api/bulk.py:40）
   B 整批回滚并返回错误（调用方须处理全量失败）
   C 其他（说明）
   未答默认：A
```

**待答期间**：不依赖答案的调查、只读分析与无冲突模块继续；依赖答案的核心实现暂停。确需先行实现时只在假设可逆且已获授权时进行，并单列「按假设 X 实现，未确认」，不得混入已确认需求。

**记录**：答复或采用的默认项写入账本或交接，仍未确认的解读列为待验证项；同一问题不重复提问，换实例或压缩上下文后再问一遍也属重复。

**子代理**：子代理不得直接向用户提问，也不得用猜测填补缺失意图；把已调查事实与候选选项返回主代理，由主代理合并成一次提问。宿主有结构化提问通道（如 interview 类工具）时经其转交，否则以纯文本编号选项给出。

## 拆分

按可以验收的行为或稳定接口拆任务；每项包含目标、依赖、写入边界和验证方法。共享数据模型、协议与跨层接口先明确归属，再排依赖顺序。

验证步骤按 [测试硬约束](../SKILL.md#测试硬约束) 组织：同一行为的数据变体成组，独立检查列为同一并行批次，仅真实依赖或冲突项列为串行并说明原因；不把每个 helper、断言或文件拆成独立的“实现—测试—等待”阶段。

默认一个开发者连续完成相关改动，按可验收阶段拆分，保持单一写入者。在阶段边界验证当前行为与契约并更新进度；需要接力或提前锁定高风险契约时，按 [编排规则](orchestration.md#审查时机) 交接或审查。阶段数、文件数与工具调用次数是调查线索，不单独触发换人或独立审查。

## 可交接计划

需要恢复、跨阶段交接或用户要求时，把计划落盘并遵守以下契约；简单任务仍留在对话，不无条件生成文件。

- 头部：目标一句话、验收条件、范围与全局约束（版本、命名、平台要求按原文复制）。
- 每个任务：创建/修改/测试的准确路径；消费与产出的接口签名（后续任务引用的类型、函数名必须已在前序任务定义）；步骤为可执行动作，代码步骤附具体代码或明确依据，验证步骤附命令与预期结果；给出提交边界。
- 审查重点：列出与当前任务有关、容易遗漏的输入、状态或失败顺序，将可执行检查归入对应任务；尚未验证的条件明确保留，供独立审查追踪。
- 步骤给出可执行细节，明确错误处理、校验、边界与测试；禁止占位符（TBD、稍后补充、写相应测试、与任务 N 相同），未确定项明确标注待核实。自检需求覆盖、接口一致性、占位符与未解决决策。计划只记录实施者需要的决策，已有依据用路径引用。

命令未核实可用时标为待核实，不编造路径或测试结果。计划保存到项目既有文档位置或任务临时目录，不无条件生成 specs/plans 文件。

执行中仅当新证据改变范围、契约或顺序时更新计划。修复已确认的需求内缺陷无需重新走脑暴。
