# 设计与计划

只补足会改变实现的决策。先利用代码、调用方、现有约定和用户已给的条件；设计已确定时在用户请求的交付范围内继续，不重新要求确认。

## 深度选择

| 情况 | 足够的产物 |
| --- | --- |
| 清楚的局部改动 | 一句目标与验证方式，无独立设计文档 |
| 目标清楚、涉及多个步骤 | 简短计划：行为、修改边界、依赖、验证 |
| 新产品行为或多种实质不同方案 | 先列目标/非目标，比较真正有差别的方案并给出推荐与代价 |
| 跨模块重构、协议变更、迁移或长任务 | 可交接设计和计划：契约、数据/状态归属、兼容策略、失败恢复、阶段验收 |
| 只问可行性或快速结论（spike） | 一句待验证问题、最小实验方案、结论或建议；产物标注 throwaway，不并入实现 |

脑暴不是固定的开工关卡。只有当问题尚未明确或方案会改变用户体验、兼容、成本及范围时才展开；不为凑选项提出明显较差方案。常规技术选择由代理在已有授权内完成，标明关键假设。

## 澄清

- 把用户意图转换为可观察的结果，不从准备采用的实现倒推需求。
- 问会影响决策的问题；能从仓库验证的不问用户。必须等答案的部分暂停，独立部分继续。
- 用户说“先设计”“先给计划”时只交付该产物；用户已要求实现时不因设计或计划阶段结束再次询问“是否开始”。
- 真正缺少范围授权或存在不可替代的产品选择时，给出已调查的事实、推荐和需要用户决定的一点，不让用户批准空泛方案。

## 拆分

按可以验收的行为或稳定接口拆任务；每项包含目标、依赖、写入边界和验证方法。共享数据模型、协议与跨层接口先明确归属，再排依赖顺序。

不为了使用子代理拆成大量碎片，不按固定行数或分钟数拆分。默认一个开发者连续完成相关改动；独立调查可并行，代码写入按照编排模块保持单一写入者。

## 可交接计划

需要恢复、跨阶段交接或用户要求时，把计划落盘并遵守以下契约；简单任务仍留在对话，不无条件生成文件。

- 头部：目标一句话、验收条件、范围与全局约束（版本、命名、平台要求按原文复制）。
- 每个任务：创建/修改/测试的准确路径；消费与产出的接口签名（后续任务引用的类型、函数名必须已在前序任务定义）；步骤为可执行动作，代码步骤附具体代码或明确依据，验证步骤附命令与预期结果；给出提交边界。
- 禁止占位符：不写“TBD/稍后补充/写相应测试/与任务 N 相同”；错误处理、校验、边界和测试必须具体。
- 自检：逐项核对需求与验收是否都有任务覆盖，扫描占位符，核对类型、签名与命名前后一致；发现问题就地修正。

命令未核实可用时标为待核实，不编造路径或测试结果。计划保存到项目既有文档位置或任务临时目录，不无条件生成 specs/plans 文件。

执行中仅当新证据改变范围、契约或顺序时更新计划。修复已确认的需求内缺陷无需重新走脑暴。
