# 新业务接入指南

本指南面向第一次使用 EasyTest 的业务测试人员，以“查询用户接口”为例，完成从创建测试项目到运行真实请求、查看报告和接入 CI 的流程。

先完成第 1～5 节，跑通一个接口；再按需要阅读多步骤场景、Mock、快照和 CI。示例接口、地址与数据是约定示例，需要替换为公司测试环境的实际接口。

尚未准备公司接口时，可以先运行 [JSONPlaceholder Demo](../examples/jsonplaceholder/README.md)：
已提供 Excel 用例和配置，无需账号，支持默认离线和公开接口 live 两种方式。

如由 AI 助手协助接入或执行，请同时提供 [《AI 接入与执行指南》](AI接入与执行指南.md)，
其中约定了用例编辑、运行范围、结果读取与失败重试方式，并提供可直接使用的任务模板。

## 1. 准备环境与接口信息

### 谁负责什么

| 角色 | 主要工作 |
| --- | --- |
| 业务接入负责人 | 安装框架、配置接口和认证，维护公司 SDK、RPC、UI 等适配器 |
| 用例维护人员 | 编辑 Excel 中的请求、变量、步骤和预期，运行测试并分析报告 |
| 框架维护人员 | 维护 EasyTest 核心代码和框架单测，提供可安装版本 |

普通业务项目无需复制或修改 `CaseRunner`、Executor、框架单测。`easytest init` 会生成业务项目自己的 `test_cases.py`。

### 本地准备

- 安装 Git 和 [uv](https://docs.astral.sh/uv/getting-started/installation/)，确认 `uv --version` 能正常执行。
- 使用 Python 3.12 或 3.13；下面统一使用 3.12，`uv sync --python 3.12` 可按需准备该版本。
- 准备 Excel 或能保存 `.xlsx` 的表格工具。
- 获取公司测试环境的服务地址、认证方式、接口定义和可用测试数据；先确认同一接口能用公司的调试工具正常调用。

后文的命令默认使用 macOS / Linux 的终端。Windows PowerShell 的虚拟环境激活命令单独给出。

## 2. 创建独立业务测试项目

### 2.1 先验证框架和离线示例

Clone 仓库后，进入包含 `pyproject.toml` 的 `easytest/` 目录：

```bash
cd /你的路径/easy_suite/easytest
uv sync --python 3.12 --no-dev
uv run easytest init ../my_tests
uv run easytest run --root ../my_tests
```

`my_tests` 必须是新目录或空目录。首次运行走离线 Mock，无需真实账号或服务；正常情况下会执行 `http.demo` 用例，并生成 `my_tests/artifacts/report.html`。终端摘要中的 `mocked: true` 表示使用了模拟响应。

### 2.2 给业务项目安装独立环境

接着进入刚创建的业务项目：

```bash
cd ../my_tests
uv venv --python 3.12
uv pip install ../easytest
source .venv/bin/activate
easytest run
pytest
```

Windows PowerShell 将激活命令换为：

```powershell
.\.venv\Scripts\Activate.ps1
```

这里的 `../easytest` 是框架源码目录。**当前包尚未发布至 PyPI**，不能假定执行 `pip install easytest` 就能安装到本仓库的框架。也可以安装维护者提供的 wheel，CI 示例见第 11 节。

后文除明确标注外，都在 `my_tests/` 目录、已激活的业务虚拟环境中执行。这个最小业务项目没有 `pyproject.toml`，直接使用 `easytest` 和 `pytest` 即可。

### 2.3 认识生成的目录

```text
my_tests/
├── cases/
│   ├── demo.xlsx             日常维护的 Excel
│   └── demo.json             自动编译结果
├── config/
│   ├── operations.json       接口、SQL 或 handler 定义
│   ├── runtime.json          默认 Profile、数据库写权限等
│   ├── profiles.json         offline-strict / live 运行预设
│   └── mock_profiles.json    离线模拟响应
├── test_cases.py             业务 pytest 入口
├── pytest.ini               业务用例收集配置
├── AI_GUIDE.md              版本匹配的 AI 操作指南及随包契约入口
├── .gitignore
└── README.md
```

`.env`、`.env.example` 需要在下一节自行创建；`artifacts/` 在运行后生成。未启用快照时，不需要 `snapshots.json` 或基线文件。

`easytest list --root .` 可只读查看启用用例与全部 operation 名称，无需真实凭据。
`run` 和 `validate` 可追加 `--case-id http.demo` 精确选择；重复参数选择多个 ID，
按来源顺序处理，未知、禁用或空 ID 失败。
普通业务项目只维护 XLSX，并将确定性生成的同名 JSON 一起提交，
同时获得表格编辑体验和 Git diff/审查能力。JSON-only 仅作为无人工维护需求的
显式高级模式，格式见 [安装包契约](../src/easytest/CONTRACT.md#来源与字段)。

## 3. 接入第一个真实 HTTP 接口

本例约定接口为：

```text
GET /users/1001
Authorization: Bearer <测试 Token>
```

成功时 HTTP 状态码为 `200`，响应 JSON 为：

```json
{
  "code": "SUCCESS",
  "data": {
    "id": 1001,
    "name": "张三",
    "status": "ACTIVE"
  }
}
```

接入公司接口时，将 URL、认证头、用户 ID 和预期字段一起替换。示例中的 `example.invalid` 是说明用地址，不提供真实服务。

### 3.1 创建环境配置

在业务项目根目录创建 `.env.example`：

```dotenv
BASE_URL=https://test-api.example.invalid
HTTP_TOKEN=replace_with_your_test_token
```

复制为 `.env`，再填入实际值：

```bash
cp .env.example .env
```

`BASE_URL` 在本例中不带末尾 `/`；`HTTP_TOKEN` 只填写 Token 本身，下面的配置会添加 `Bearer ` 前缀。实际认证如果使用 `X-API-Key` 等头，按接口要求调整。

`.env.example` 只保存变量名和示例值，可以提交；真实 `.env` 已被生成的 `.gitignore` 忽略。Token、密码不要填写到 Excel 或提交到配置 JSON。

框架自动读取**业务项目根目录**的 `.env`，保存在项目私有映射中，进程环境变量优先，不会修改进程环境。业务 handler 需要项目环境时可读取 `context.environment`。Token 的获取和续期由公司的认证工具或 CI 前置步骤完成，框架不会自动登录或刷新 Token。

### 3.2 定义接口

将 `config/operations.json` 替换为：

```json
{
  "operations": {
    "http.get_user": {
      "executor": "http",
      "method": "GET",
      "url": "${BASE_URL}/users/{user_id}",
      "headers": {
        "Authorization": "Bearer ${HTTP_TOKEN}"
      },
      "timeout": 10,
      "expected_status": [200]
    }
  }
}
```

其中：

| 写法 | 来源与用途 |
| --- | --- |
| `${BASE_URL}`、`${HTTP_TOKEN}` | 在 operation 配置中读取环境变量 |
| `{user_id}` | URL 路径占位符，由步骤 `request.path` 提供 |
| `${variables.user_id}` | 在 Excel 请求或断言中读取当前用例变量 |
| `${steps.created.body.data.id}` | 在后续步骤中读取前一步保存的输出 |

不要把这些写法混用。用例变量和步骤结果应写在 Excel 的 `request` / `expect` 等模板字段中，不能直接放进 operation 配置并期待自动解析。

### 3.3 编辑 Excel

脚本或 AI 优先使用 `easytest edit cases/demo.xlsx --patch edit.json` 按 Case/Step ID
提交结构化操作；命令会校验整个工作簿、检测并发改动并同步生成 JSON。人工维护时
再按下面方式直接编辑表格。

打开已有的 `cases/demo.xlsx`，取消隐藏所有列，将原有示例数据替换为以下内容。工作表名称必须保留为小写 `cases` 和 `steps`。

**`cases` 工作表：**

| case_id | case_name | case_type | enabled | variables |
| --- | --- | --- | --- | --- |
| user.get | 查询已有用户 | http | true | `{"user_id":1001}` |

**`steps` 工作表：**

| case_id | step_id | order | executor | operation | request | expect |
| --- | --- | --- | --- | --- | --- | --- |
| user.get | get_user | 1 | http | http.get_user | `{"path":{"user_id":"${variables.user_id}"}}` | `{"$.status_code":200,"$.body.code":"SUCCESS","$.body.data.id":"${variables.user_id}"}` |

表格中的反引号只用于文档排版，**不要复制到 Excel 单元格中**。每段 JSON 放在一个单元格里，使用英文双引号，不写公式或 JSON 注释。

此处变量 `user_id` 是数字 `1001`。完整的 `${variables.user_id}` 占位符会保留数字类型，所以断言能与响应中的数字 ID 比较。

保存 Excel 后，不需要手工修改 `demo.json`；下一次执行会自动编译并更新它。

### 3.4 发出真实请求

先检查本次执行配置；此命令不会发出请求，也不会改写 Excel、JSON、快照或报告：

```bash
easytest validate cases/demo.xlsx --profile live
```

通过后再运行：

```bash
easytest run cases/demo.xlsx --profile live
```

`run` 本身也会先检查整批用例。后续步骤引用了不存在的 operation、缺少已知变量、
HTTP 参数拼写错误等静态问题，会在第一个真实请求前报错。
`validate` 的成功 JSON 会在 `data.deferred` 列出动态项：这表示依赖前序响应、运行时状态或
handler 的检查需要在执行时完成，不代表接口已经测试通过。
离线预检不会要求真实服务凭据；`live` 也仍遵循 Case / Step 显式配置的 Mock。

确认三个结果：

1. 终端命令成功结束，JSON 顶层 `status=passed`，`data.cases[].steps[]` 中步骤的 `mocked` 为 `false`。
2. 报告中的 `user.get` 用例和 `get_user` 步骤通过。
3. 响应里的用户 ID、业务状态等确实来自目标测试环境。

`live` 表示允许真实执行，**不负责选择测试环境地址，也不会强制清除用例显式指定的 Mock**。本例没有在 Case 或 Step 上指定 Mock，因此会发出真实 HTTP 请求。

初始化项目默认选择 `offline-strict`。替换接口后，原有离线 Mock 只认识 `http.ping`，直接执行不带 `--profile live` 的命令会被严格模式阻止；需要离线调试时按第 8 节补充 Mock。

## 4. 常用请求和断言怎么填写

### 请求字段

以下都是 Excel `request` 单元格的写法，按接口需要选用：

| 请求内容 | 示例 |
| --- | --- |
| URL 路径参数 | `{"path":{"user_id":1001}}` |
| GET 查询参数 | `{"params":{"page":1,"page_size":20}}` |
| POST JSON 请求体 | `{"json":{"name":"测试用户","status":"ACTIVE"}}` |
| 表单参数 | `{"data":{"name":"测试用户"}}` |
| 覆盖本步骤超时 | `{"timeout":20}` |
| 同时传路径和查询参数 | `{"path":{"user_id":1001},"params":{"include":"roles"}}` |

`request` 会与 operation 配置合并，同名设置由步骤覆盖；嵌套对象递归合并。HTTP JSON 请求体使用 `json`，不能直接把业务字段放在 `request` 顶层。
框架会拒绝 `jsno` 等未知传输字段；`json`、`params` 内部的业务字段不受这份白名单限制。
Excel 的列名同样严格检查，额外说明请写在单元格批注中。

### 响应与断言

HTTP 执行器返回的结构包含 `status_code`、`headers`、`body`、`elapsed_ms`、`url` 和 `attempts`。服务端 JSON 位于 `body` 下，因此业务字段断言通常以 `$.body` 开头。

简单相等判断：

```json
{"$.status_code":200,"$.body.code":"SUCCESS","$.body.data.status":"ACTIVE"}
```

多个允许值或包含判断：

```json
{
  "checks": [
    {"path": "$.status_code", "equals": 200},
    {"path": "$.body.data.status", "in": ["ACTIVE", "PENDING"]},
    {"path": "$.body.data.name", "contains": "张"}
  ]
}
```

路径支持对象字段和数组下标，例如 `$.body.items[0].id`；不支持完整 JSONPath 的过滤表达式或通配符查询。字段不存在会报错；数字 `1001` 与字符串 `"1001"` 不相等。
布尔与数字递归区分，`true` 不等于 `1`、`false` 不等于 `0`；数字 `1` 和 `1.0` 相等。
比较操作符只能使用 `equals`、`contains`、`in`。例如误写成 `equal`、
只填写 `path`、填写空的 `checks`，都会明确失败；不需要断言时留空单元格。

### 测试预期的 404

如果 operation 配置了 `expected_status: [200]`，返回 404 会在执行阶段报错，尚未进入 Excel 断言。测试错误场景时，需要同时调整本步骤允许的 HTTP 状态码和断言。

例如给 `cases` 新增一个 `user.missing` 用例：

| case_id | case_name | case_type | enabled | variables |
| --- | --- | --- | --- | --- |
| user.missing | 查询不存在的用户 | http | true | `{}` |

再给它填写以下步骤：

| case_id | step_id | order | executor | operation | request | expect |
| --- | --- | --- | --- | --- | --- | --- |
| user.missing | get_missing | 1 | http | http.get_user | `{"path":{"user_id":0},"expected_status":[404]}` | `{"$.status_code":404,"$.body.code":"NOT_FOUND"}` |

本例约定 `0` 是不存在的 ID，错误响应为 `{"code":"NOT_FOUND"}`；实际值以业务接口约定为准。

## 5. 查看报告和定位失败

每次执行默认输出 `artifacts/report.html`。双击即可用浏览器离线查看；macOS 也可以执行：

```bash
open artifacts/report.html
```

建议按这个顺序检查：

1. 看总用例数、失败数和通过率，确认实际运行了预期用例。
2. 搜索用例 ID 或筛选失败，展开用例和具体步骤。
3. 根据来源文件、`steps` 行号和 operation 回到 Excel 或接口配置。
4. 看步骤阶段：`preflight` 为执行前校验，`prepare` 为准备，`execute` 为执行，`assertion` 为断言，`snapshot` 为快照比对。
5. 有快照差异时，查看自动分类、字段分组以及期望 / 实际值；网络错误和普通断言失败不会伪造成快照 diff。

请求、响应和差异值经过敏感字段脱敏，长值会截断。网页不包含任意异常原文和完整调用栈，具体异常继续查本地终端。报告中“请求”主要展示步骤输入，不是完整的网络抓包。

点击“下载报告数据”可导出 JSON；点击“导出 PDF”直接下载完整报告，包含全部用例、步骤和差异，不受网页筛选或折叠状态影响。

自动化读取可执行 `easytest run --result artifacts/result.json`。成功、失败和可捕获中断均使用 `schema_version=1` 的统一 JSON 封装，`data` 是报告，`errors` 是安全错误信息；文件内容与 stdout 相同，日志和事件输出至 stderr。`--no-report` 可单独关闭 HTML。

文件名使用本地时间，精确到秒，例如：

```text
easytest_report_20260926161908.pdf
easytest_report_20260926161908.json
```

默认 HTML 路径会覆盖上次结果。需要留档时显式指定：

```bash
easytest run cases/demo.xlsx --profile live --report artifacts/regression_20260926161908.html
```

这里的日期是示例，实际运行时自行替换；CI 更适合按流水线构建记录归档。

## 6. 把单接口扩展成业务流程

以“创建用户 → 查询刚创建的用户”为例。假设 `POST /users` 接受 `{"name":"..."}`，返回 HTTP 201 和 `{"code":"SUCCESS","data":{"id":1002}}`。

在 `operations.json` 的 `operations` 对象中新增以下条目，保留已有的 `http.get_user`：

```json
{
  "http.create_user": {
    "executor": "http",
    "method": "POST",
    "url": "${BASE_URL}/users",
    "headers": {
      "Authorization": "Bearer ${HTTP_TOKEN}"
    },
    "timeout": 10,
    "expected_status": [201]
  }
}
```

这是需要合并的条目，不能直接替换整个配置文件。给 `cases` 工作表追加一行：

| case_id | case_name | case_type | enabled | variables |
| --- | --- | --- | --- | --- |
| user.create_then_get | 创建后查询用户 | http | true | `{}` |

在 `steps` 工作表添加可选列 `save_as`，并追加：

| case_id | step_id | order | executor | operation | request | expect | save_as |
| --- | --- | --- | --- | --- | --- | --- | --- |
| user.create_then_get | create_user | 1 | http | http.create_user | `{"json":{"name":"autotest_${generate.uuid}"}}` | `{"$.status_code":201,"$.body.code":"SUCCESS"}` | created |
| user.create_then_get | get_created | 2 | http | http.get_user | `{"path":{"user_id":"${steps.created.body.data.id}"}}` | `{"$.status_code":200,"$.body.data.id":"${steps.created.body.data.id}"}` | |

`save_as=created` 保存的是第一步完整输出，后续通过 `steps.created` 引用。不设置 `save_as` 时用 `step_id` 引用，例如 `steps.create_user`；设置别名后使用别名。

`${generate.uuid}` 每个 Case 生成一次，Case 内保持稳定。步骤间只共享当前 Case 的变量、输出和状态，不应依赖另一条 Case 先执行。

该场景会创建测试数据，需要业务方提供回收方式。一个步骤失败会停止当前 Case 的后续步骤，因此不能只依赖最后一个步骤执行清理；需要可靠清理时，由接入负责人在 pytest fixture 的收尾逻辑中处理，或使用测试环境的数据回收机制。

HTTP POST 默认不会自动重试。只有接口具备幂等保障时，才由接入负责人显式配置 POST 重试。

### 数据清理示例

业务项目可以提供一个已有公司 SDK 的 `business_sdk` fixture，再用 yield 管理造数与回收。
下面假设 SDK 有 `create_user/delete_user`，且查询用例用 `variables.user_id`，
实际方法与返回字段需由接入负责人适配。只选择对应查询 Case，避免套用于创建流程：

```python
from dataclasses import replace
import pytest

@pytest.fixture
def created_user(business_sdk):
    user = business_sdk.create_user(name="easytest temporary user")
    try:
        yield user
    finally:
        business_sdk.delete_user(user["id"])

def test_case(table_case, case_runner, created_user):
    case = replace(
        table_case,
        variables={**table_case.variables, "user_id": created_user["id"]},
    )
    case_runner.run(case)
```

断言失败仍会进入 fixture 的 finally；删除失败会由 pytest 报告为 teardown 失败。
SDK 创建调用超时或中断时可能已写入但尚未返回 ID，应使用业务幂等键/查询/回收机制确认，
不能认为 finally 可处理所有未知结果。也可以在一个业务 handler 内用同样的
`try/finally` 封装流程；Runner 只负责资源关闭，不代替业务回收。

## 7. 切换环境和认证

环境地址和账号来自 `.env` 或进程环境；Profile 控制运行策略，两者分别配置。

| 设置 | 作用 |
| --- | --- |
| `BASE_URL`、`HTTP_TOKEN` | 本指南 operation 引用的业务环境地址与认证 |
| `--profile offline-strict` | 只允许返回 Mock 结果，不进入真实执行器 |
| `--profile live` | 允许真实执行，保留用例显式指定的 Mock |
| `--run-mode read/write/baseline` | 控制快照比对、补齐和更新 |
| `--allow-db-write` | 单独开启数据库执行器的写权限 |

不要把 `BASE_URL` 加进 `profiles.json` 并期待它随 Profile 改变；当前 Profile 不支持任意环境变量或配置覆盖，也没有 `--env qa` 选项。

本地切换环境时，更新 `.env` 后重新运行命令；Notebook 关闭旧 Session 并新建即可重新读取。也可以在终端中设置环境变量；这些值会优先于 `.env`。避免把真实 Token 写进可提交脚本或命令历史。

`read` 指的是快照读取，不表示 HTTP 只读：只要允许真实执行，配置的 POST 仍然会发出。数据库写权限与快照模式独立，初始化项目默认关闭数据库写入。

## 8. 按需保留离线 Mock

如果希望最初的 `user.get` 用例在没有网络和账号时也能运行，可将 `config/mock_profiles.json` 配置为：

```json
{
  "profiles": {
    "offline": {
      "http.get_user": {
        "kind": "response",
        "response": {
          "status_code": 200,
          "body": {
            "code": "SUCCESS",
            "data": {"id": 1001, "name": "张三", "status": "ACTIVE"}
          }
        }
      }
    }
  }
}
```

这里模拟的是执行器输出，因此必须包含 `status_code` 和 `body`，不能只写服务端业务 JSON。

只选择最初的查询用例执行：

```bash
pytest --case-source cases/demo.xlsx -k "user.get" --profile offline-strict
```

该 Mock 返回固定用户，只覆盖最初的查询场景，不适用于 404 或创建流程。新增场景需要配套的 Mock，或者明确选择 `live`。

Mock 优先级是 Step 显式配置 → Case 的 Mock Profile → 运行 Profile 的 Mock Profile。Excel 步骤 `mock` 列填写 JSON 布尔值 `false` 可以禁用 Mock 回退，但 `offline-strict` 此时仍会阻止真实执行。

## 9. 按需启用快照和差异归类

简单状态码和业务字段校验使用 `expect` 即可。需要比较较完整且稳定的响应时，再启用快照。

### 9.1 定义比较规则

创建 `config/snapshots.json`：

```json
{
  "profiles": {
    "default": {
      "user_detail": {
        "kind": "response",
        "select": "$.body.data",
        "ignore_paths": ["$.updated_at"]
      }
    }
  }
}
```

本例只比较 `body.data`，忽略其中可能变化的 `updated_at`。忽略路径相对于 `select` 选中的对象，所以写 `$.updated_at`，不是 `$.body.data.updated_at`。

给 `steps` 新增 `snapshot` 列，**仅在最初 `user.get` 用例的 `get_user` 步骤**填写：

```json
{"rule":"user_detail","name":"user_detail"}
```

`cases` 的 `snapshot_profile` 未填写时默认为 `default`。先选择稳定测试用户，避免把每次新建用户的随机 ID、名称作为固定基线比较。

### 9.2 建立与使用基线

首次确认响应正确后，创建缺失基线：

```bash
pytest --case-source cases/demo.xlsx -k "user.get" --profile live --run-mode write
```

默认文件后端会生成 `snapshots/user.get/user_detail.json`。人工查看内容，确认后作为业务项目基线维护。后续回归：

```bash
pytest --case-source cases/demo.xlsx -k "user.get" --profile live --run-mode read
```

基线缺失或出现差异都会失败，报告会按字段新增、缺失、类型、数值、文本等变化自动归类。分类描述变化，不自动判断是不是业务缺陷。

只有业务变更已确认、需要替换基线时，才执行以下命令（macOS / Linux）：

```bash
CONFIRM_BASELINE=1 pytest --case-source cases/demo.xlsx -k "user.get" --profile live --run-mode baseline
```

`write` 只补齐缺失基线，已有内容不同时会失败；不能用它覆盖差异。常规 CI 使用 `read`，不要自动把失败结果更新成基线。

需要 SQLite 历史后端、保留策略或更复杂的归一化规则时，参阅 [框架 README 的 Snapshot 说明](../README.md#snapshot)。

## 10. 日常维护与运行范围

常用命令：

```bash
easytest run --profile live
easytest run cases/demo.xlsx --profile live
easytest list cases/demo.xlsx
easytest validate cases/demo.xlsx --case-id user.get --profile live
easytest run cases/demo.xlsx --case-id user.get --profile live
pytest --case-source cases/demo.xlsx --profile live
pytest --case-source cases/demo.xlsx -k "user.get" --profile live
easytest edit cases/demo.xlsx --patch edit.json
easytest compile cases/demo.xlsx
easytest compile cases --check
```

不传来源默认发现 `cases/`；传路径选择文件或目录，`--case-id` 精确选择。
pytest 的 `-k` 是关键词匹配；需要精确时用 `'test_cases.py::test_case[user.get]'`。
普通 compile 更新同名 JSON；`--check` 不写文件，检查每份 JSON 是否与 XLSX、
当前编译器版本完全同步。两者都不发出业务请求。

`case_id` 在同次运行的所有工作簿中必须唯一；每个 Case 内的 `step_id` 和正整数 `order` 必须唯一。复制用例时同时修改 `cases` 和 `steps` 中的关联 ID。ID 使用字母、数字、`.`、`_`、`-`，中文名称填写在 `case_name`。

临时停用用例时，在 `cases.enabled` 填 `false`。如果全部用例都禁用，框架会报“没有启用的用例”，不会当作成功回归。

普通项目只编辑 XLSX，并提交 Excel 和生成的同名 JSON；JSON 用于 Git diff、
代码审查、AI 分析和执行，不是第二份权威源。提交前运行
`easytest compile cases --check`。生成 JSON 记录 XLSX 哈希和编译器版本。
重命名或删除工作簿时同步处理旧 JSON，否则会报 `ORPHAN_COMPILED_JSON`。
JSON-only 仅适合纯代码/机器生成项目，必须显式声明 `source_mode: "json"`；
删除 `source` 不会隐式切换模式。
文件快照在 Case 成功后统一提交；Excel 打开的 `~$` 临时文件会被忽略。

报告、虚拟环境和本地凭据无需提交。单个步骤失败会停止该 Case；普通执行错误不会阻止 CLI 继续运行其他 Case，全部执行后以失败状态退出。pytest 按其测试运行规则汇总结果。`Ctrl+C` 等中断会停止运行。

## 11. 接入 CI

### 11.1 准备框架安装包

由框架维护者在**框架目录**构建：

```bash
uv build --wheel
```

当前版本输出 `dist/easytest-0.2.0-py3-none-any.whl`。将确定版本的 wheel 交给业务项目，或上传到公司的制品仓库供流水线下载。下面示例约定 CI 开始测试前，wheel 已位于业务项目的 `vendor/` 目录。

框架升级时显式修改安装版本；不要依赖 CI 机器上碰巧已有的框架源码。

### 11.2 配置流水线变量

在 CI 的变量或密钥管理界面设置 `BASE_URL`、`HTTP_TOKEN`，确保执行节点可访问公司测试环境。真实凭据不写进 YAML，也不打印到日志。已采用文件快照时，业务仓库应包含经确认的基线。

在干净的 Python 3.12 环境中，核心执行命令为：

```bash
python -m pip install vendor/easytest-0.2.0-py3-none-any.whl
easytest compile cases --check
python -m pytest test_cases.py --profile live --run-mode read --easytest-root . --easytest-report artifacts/report.html --junitxml=artifacts/junit.xml
```

默认发现 `cases/` 中的业务用例。若只运行部分文件，可追加 `--case-source cases/demo.xlsx`。
同步检查应在测试前执行，避免 CI 使用未提交或手工修改的编译产物。

### 11.3 GitLab CI 示例

以下内容保存为**业务项目根目录**的 `.gitlab-ci.yml`。运行前需准备好上一节约定的 wheel 和 CI 变量：

```yaml
stages:
  - test

api_regression:
  stage: test
  image: python:3.12-slim
  script:
    - python -m pip install vendor/easytest-0.2.0-py3-none-any.whl
    - easytest compile cases --check
    - python -m pytest test_cases.py --profile live --run-mode read --easytest-root . --easytest-report artifacts/report.html --junitxml=artifacts/junit.xml
  artifacts:
    when: always
    expire_in: 14 days
    paths:
      - artifacts/
    reports:
      junit: artifacts/junit.xml
```

JUnit XML 用于 CI 的测试结果统计，HTML 用于下载查看步骤和 diff。`when: always` 让测试失败时也尝试收集报告；不要用 `|| true` 掩盖测试退出码。依赖安装失败或进程被强制终止时，报告可能尚未生成。

其他 CI 平台采用相同的安装、运行和失败时归档流程。当前 EasyTest 网页报告支持顺序 pytest 执行，不要添加 pytest-xdist 的 `-n` 并行选项。

## 12. 常见问题排查

| 现象 / 错误 | 优先检查与处理 |
| --- | --- |
| `easytest` 找不到或 pytest 不认识 `--profile` | 确认已激活业务 `.venv`，并在该环境安装本仓库框架包；pytest 插件通常随安装自动加载，检查是否禁用了插件自动加载 |
| `init requires a new or empty directory` | 换一个新目录，或使用已有业务项目；不要在非空业务目录重新初始化 |
| `unknown profile` | 查看本项目 `profiles.json` 是否定义该名称；Profile 名称不会自动变成环境名称 |
| `strict profile blocked real execution` | 当前为严格离线模式；补充对应 Mock，或确认目标环境后使用 `--profile live` |
| 选择了 `live`，结果仍显示 Mock | 检查 Excel 的 `mock`、`mock_profile`；运行 Profile 不会清除 Step / Case 的显式 Mock |
| `required environment variable ... is not set` | `.env` 是否位于业务根目录、变量名是否一致、`--root` / `--easytest-root` 是否指向正确项目 |
| 修改 `.env` 后仍访问旧地址 | 当前进程或终端环境变量优先于 `.env`；检查已有变量，并重建 Runner / NotebookSession |
| 401 / 403 | 检查 Token 有效期、Header 名称、`Bearer` 前缀是否重复、账号权限及是否与当前环境匹配 |
| 连接超时、代理或证书错误 | 先确认同一机器能访问目标环境，再核对 VPN、代理和公司 CA；HTTP operation 可按需设置 `timeout`、`verify` 等 |
| `unknown operation` 或 executor 不匹配 | Excel `operation` 必须与配置 key 一致，Excel 与配置中的 `executor` 也要一致 |
| URL 中仍有 `{user_id}` 或缺少路径参数 | 在 `request.path` 中提供同名字段；路径占位符不用 `${...}` 写法 |
| `must contain valid JSON` | 按报错单元格检查英文双引号、逗号、布尔值；去掉文档反引号、中文引号和注释 |
| 缺少 sheet / 列、存在空表头或公式 | 保留 `cases`、`steps` 和必填列；删除多余的格式化空列或补齐列名，公式改成实际值 |
| `duplicate case id` / 步骤 ID 或 order 重复 | 检查复制的行和其他工作簿，尤其是重命名后遗留的 JSON |
| `no enabled cases` / 没有发现用例 | 检查路径、`.xlsx` 文件和 `enabled`；不要把空目录或全部禁用当成正常通过 |
| `path ... does not exist` | HTTP 业务字段从 `$.body` 开始；核对数组下标、字段名、JSON 是否实际解析成功及 `save_as` 别名 |
| HTTP 状态码检查先失败，预期断言没执行 | 错误场景需要在步骤请求里覆盖 `expected_status`，例如 `[404]` |
| 快照不存在 | 首次接入尚未建立基线，确认响应后用 `write` 创建，再用 `read` 回归 |
| 快照每次都变化 | 检查选择范围与时间戳、随机 ID 等动态字段；按业务含义配置忽略或归一化，确认变更后再更新基线 |
| 数据库写入被拒绝 | 同时检查 `--allow-db-write`、连接 `read_only`、operation 的 `write` 与 SQL 类型；快照模式不等于写权限 |
| pytest 没有生成 HTML | 使用生成的业务 `test_cases.py`，或显式加 `--easytest-report`；检查是否关闭报告、使用了 `-n`，并查看终端提示 |

## 13. HTTP 之外的接入

| 需求 | 接入方式 |
| --- | --- |
| 数据库准备和校验 | 接入负责人在 runtime 中配置连接，在 operation 中维护固定的参数化 SQL；用例只提供绑定参数 |
| RPC | 配置 endpoint、来自环境变量的鉴权和 `package.module:function` handler，将公司 SDK 封装在业务可安装包中 |
| UI | 由 handler 封装实际 UI 操作，返回输出和可选截图路径；仅填写 Excel 不会自动生成浏览器操作 |
| 复杂业务流程 | 在同一 Case 编排 HTTP / RPC / Database / UI / Scenario 步骤，或将公共操作封装为 handler |

handler 所在包必须安装在运行测试的 Python 环境中。混合流程的 `case_type` 可使用 `scenario`，每个步骤仍填写实际 executor。
可直接安装并运行 [独立业务 handler 示例](../examples/business_handler/README.md)。
普通业务字典（包括 output 字段）完整保留；截图、metadata 通过
`from easytest import ExecutionResult` 显式返回。旧版包装字典迁移见
[0.2.0 迁移说明](0.2.0迁移说明.md)。

具体签名、配置字段和运行边界参阅 [框架 README](../README.md#操作与适配器)。希望在 VS Code 中交互调试时，参阅 [Notebook 使用说明](../README.md#notebook-手动测试) 和 [仓库示例 Notebook](../notebooks/manual_test.ipynb)。
