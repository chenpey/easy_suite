# 新业务接入指南

本指南面向首次接入 EasyTest 的业务测试人员。字段、错误码和完整 API 以安装包内的
`easytest/CONTRACT.md` 为准；AI 协作另见 [AI 接入与执行指南](AI接入与执行指南.md)。

尚未准备公司接口时，可先运行
[JSONPlaceholder Demo](../examples/jsonplaceholder/README.md)。

## 1. 准备环境与接口信息

准备以下内容：

- Python 3.12 或 3.13，以及 [uv](https://docs.astral.sh/uv/getting-started/installation/)。
- 测试环境地址、认证方式和可用测试数据。
- 接口请求、响应、错误场景和业务预期。
- 写操作的数据回收方式。

职责边界：

| 角色 | 主要工作 |
| --- | --- |
| 业务负责人 | 确认环境、权限、预期和数据回收 |
| 用例维护人员 | 编辑 XLSX、执行测试、分析结果 |
| 框架维护人员 | 维护 EasyTest 核心、契约和版本 |

真实凭据不得写入 Excel、配置 JSON、代码或 Git。

## 2. 创建独立业务测试项目

在框架目录执行：

```bash
uv sync --python 3.12 --no-dev
uv run easytest init ../my_tests
uv run easytest run --root ../my_tests
```

`init` 只接受新目录或空目录。生成项目默认使用离线 Mock，包含：

```text
my_tests/
├── cases/demo.xlsx
├── cases/demo.json
├── config/
├── test_cases.py
├── pytest.ini
├── AI_GUIDE.md
├── README.md
└── .gitignore
```

需要独立环境时：

```bash
cd ../my_tests
uv venv --python 3.12
uv pip install ../easytest
source .venv/bin/activate
easytest run
```

Windows PowerShell 使用 `.\.venv\Scripts\Activate.ps1`。当前包未发布至 PyPI，
应安装指定源码目录或维护者提供的 wheel。

## 3. 接入第一个真实 HTTP 接口

以下示例假设：

```text
GET /users/1001
Authorization: Bearer <测试 Token>
```

### 3.1 创建环境配置

创建可提交的 `.env.example`：

```dotenv
BASE_URL=https://test-api.example.invalid
HTTP_TOKEN=replace_with_your_test_token
```

复制为被 Git 忽略的 `.env` 后填写真实值。进程环境优先于 `.env`；修改后需要
重新创建 Runner 或 NotebookSession。

### 3.2 定义接口

在 `config/operations.json` 中配置：

```json
{
  "operations": {
    "http.get_user": {
      "executor": "http",
      "method": "GET",
      "url": "${BASE_URL}/users/{user_id}",
      "headers": {"Authorization": "Bearer ${HTTP_TOKEN}"},
      "timeout": 10,
      "expected_status": [200]
    }
  }
}
```

`${BASE_URL}` 读取环境变量，`{user_id}` 读取步骤的 `request.path.user_id`。

### 3.3 编辑 Excel

`cases` 工作表：

| case_id | case_name | case_type | enabled | variables |
| --- | --- | --- | --- | --- |
| user.get | 查询已有用户 | http | true | `{"user_id":1001}` |

`steps` 工作表：

| case_id | step_id | order | executor | operation | request | expect |
| --- | --- | --- | --- | --- | --- | --- |
| user.get | get_user | 1 | http | http.get_user | `{"path":{"user_id":"${variables.user_id}"}}` | `{"$.status_code":200,"$.body.data.id":"${variables.user_id}"}` |

表格中的反引号仅用于文档排版。JSON 单元格使用英文双引号，不填写公式。

AI 或脚本使用结构化补丁，成功后会同步生成 JSON：

```bash
easytest edit cases/demo.xlsx --patch edit.json
```

### 3.4 发出真实请求

先只读检查：

```bash
easytest validate cases/demo.xlsx --case-id user.get --profile live
```

再执行同一范围：

```bash
easytest run cases/demo.xlsx --case-id user.get --profile live
```

确认退出状态、Case 数量及步骤 `mocked=false`。`live` 允许真实执行，但不会替你
选择测试环境，也不会清除 Case/Step 上的显式 Mock。

## 4. 请求、断言与模板

常用请求：

```json
{"path":{"user_id":1001}}
{"params":{"page":1,"page_size":20}}
{"json":{"name":"测试用户","status":"ACTIVE"}}
{"data":{"name":"测试用户"}}
```

HTTP 响应位于 `body`：

```json
{"$.status_code":200,"$.body.code":"SUCCESS"}
```

复杂断言：

```json
{"checks":[
  {"path":"$.body.data.status","in":["ACTIVE","PENDING"]},
  {"path":"$.body.data.name","contains":"张"}
]}
```

模板来源：

| 写法 | 含义 |
| --- | --- |
| `${variables.user_id}` | 当前 Case 变量 |
| `${steps.created.body.data.id}` | 前序步骤输出 |
| `${state.user.id}` | 当前 Case 状态 |
| `${generate.uuid}` | 当前 Case 内稳定的生成值 |

完整占位符保留原类型。断言支持 `equals/contains/in`，字段不存在或操作符拼错会失败。
更多字段规则见 [安装包契约](../src/easytest/CONTRACT.md#断言和模板)。

## 5. 查看报告和定位失败

默认报告为 `artifacts/report.html`，可离线打开。建议按以下顺序检查：

1. 核对总数、通过率、失败和未执行数量。
2. 按 Case ID 定位失败步骤和 Excel 行号。
3. 查看失败阶段：`preflight/prepare/execute/assertion/snapshot`。
4. 快照失败再查看差异类别、字段路径、期望和实际值。

机器读取：

```bash
easytest run --result artifacts/result.json
```

stdout 和结果文件使用相同 JSON 封装；日志及原始异常在 stderr。失败也可能生成
HTML，因此必须同时检查退出码和顶层 `status`。

## 6. 把单接口扩展成业务流程

在同一 Case 中通过 `save_as` 串联步骤：

```text
create_user  save_as=created
get_created  request={"path":{"user_id":"${steps.created.body.data.id}"}}
```

步骤只共享当前 Case 的 variables、outputs 和 state，不依赖其他 Case 的执行顺序。
POST 默认不重试；只有业务已有幂等保障时才能显式加入重试。

### 数据清理示例

清理不要放在最后一个测试步骤，因为前序失败会阻止它执行。使用 pytest fixture：

```python
import pytest

@pytest.fixture
def created_user(business_sdk):
    user = business_sdk.create_user(name="easytest temporary user")
    try:
        yield user
    finally:
        business_sdk.delete_user(user["id"])
```

请求超时仍可能已经写入。应使用业务幂等键、状态查询和回收机制确认，不能盲目重跑。

## 7. 切换环境和认证

| 设置 | 作用 |
| --- | --- |
| `.env` / 进程环境 | 地址与凭据 |
| `offline-strict` | 只允许得到 Mock 结果的步骤 |
| `live` | 允许真实执行 |
| `read/write/baseline` | 快照读取、补齐和更新 |
| `allow_db_write` | 内置数据库写权限 |

`read` 不是业务只读模式。AI 或 CI 执行真实服务时应使用受信任执行策略，格式见
[框架 README](../README.md#执行策略)。

## 8. 按需保留离线 Mock

在 `config/mock_profiles.json` 中按 operation 提供执行器输出：

```json
{
  "profiles": {
    "offline": {
      "http.get_user": {
        "kind": "response",
        "response": {
          "status_code": 200,
          "body": {"code": "SUCCESS", "data": {"id": 1001}}
        }
      }
    }
  }
}
```

Mock 输出需包含 `status_code` 和 `body`。优先级为 Step > Case Mock Profile >
运行 Profile。`mock=false` 禁用回退，但 `offline-strict` 仍会阻止真实执行。

## 9. 按需启用快照和差异归类

创建 `config/snapshots.json`：

```json
{
  "profiles": {
    "default": {
      "user_detail": {
        "kind": "response",
        "select": "$.body.data",
        "ignore_paths": ["$.updated_at"]
      }
    }
  }
}
```

在步骤的 `snapshot` 单元格填写：

```json
{"rule":"user_detail","name":"user_detail"}
```

建立及读取基线：

```bash
easytest run cases/demo.xlsx --case-id user.get --profile live --run-mode write
easytest run cases/demo.xlsx --case-id user.get --profile live --run-mode read
CONFIRM_BASELINE=1 easytest run cases/demo.xlsx \
  --case-id user.get --profile live --run-mode baseline
```

`write` 只创建缺失基线，`baseline` 才替换已有内容。文件快照在 Case 成功后统一
提交；SQLite 可保存成功历史。业务响应未经确认时不能更新基线。

## 10. 日常维护与运行范围

```bash
easytest list cases
easytest validate cases --case-id user.get --profile live
easytest run cases --case-id user.get --profile live
easytest compile cases --check
```

普通项目只编辑 XLSX，并提交 XLSX 和同名 JSON。重命名或删除工作簿时同步处理
旧 JSON。报告、虚拟环境和本地凭据不提交。

## 11. 接入 CI

```bash
python -m pip install vendor/easytest-0.2.0-py3-none-any.whl
easytest compile cases --check
python -m pytest test_cases.py \
  --profile live \
  --run-mode read \
  --easytest-root . \
  --easytest-report artifacts/report.html \
  --junitxml=artifacts/junit.xml
```

在 CI 密钥管理中设置凭据和 `EASYTEST_EXECUTION_POLICY`。失败时也归档
`artifacts/` 和 JUnit，但不要用 `|| true` 隐藏退出码。当前 HTML 报告不支持
pytest-xdist 合并。

## 12. 常见问题排查

| 现象 | 优先检查 |
| --- | --- |
| `easytest` 找不到 | 虚拟环境是否激活、wheel 是否安装 |
| `unknown profile` | `config/profiles.json` |
| strict profile 阻止执行 | 补 Mock，或确认授权后选择 live |
| live 仍显示 Mock | Step、Case 和运行 Profile 的 Mock |
| 缺少环境变量 | `.env` 位置、变量名、进程环境覆盖 |
| 401 / 403 | Token、Header、账号权限和目标环境 |
| URL 路径参数缺失 | `request.path` 与 `{name}` 是否一致 |
| JSON 或 Excel 契约错误 | 报错单元格、英文引号、列名、公式 |
| 快照缺失或变化 | 运行模式、动态字段、比较规则和业务确认 |
| 数据库写入被拒绝 | CLI 权限、连接 `read_only`、operation `write` 和 SQL 类型 |

## 13. HTTP 之外的接入

| 需求 | 接入方式 |
| --- | --- |
| Database | runtime 定义连接，operation 保存固定参数化 SQL |
| RPC | 配置 endpoint、环境变量鉴权和业务 handler |
| UI | handler 封装 UI 操作并返回可选截图 |
| 复杂流程 | 在同一 Case 编排多类步骤，或封装 scenario handler |

handler 包必须安装在测试环境中。参考
[独立业务 handler 示例](../examples/business_handler/README.md)；
精确签名见 [操作与适配器](../README.md#操作与适配器)。
